# 开发治理机制

> 版本：0.1
> 状态：草案
> 范围：本地 Agent 平台的开发流程、角色分工、测试门禁、Git 风险控制和回滚机制。

## 1. 目标

本项目会长期由人类和多个 AI Agent 协作开发。治理机制的目标不是降低开发速度，而是防止 AI 快速生成代码后造成架构失控、权限漏洞、质量不可验证和难以回滚。

核心原则：

- 规格先于实现。
- 测试先于完成声明。
- 证据先于合并。
- 主线程负责方向和质量，执行 Agent 负责边界清楚的任务。
- 任何高风险改动必须能审查、能测试、能回滚。

## 2. 角色分工

### Product Owner

由用户承担，负责：

- 定义真实需求和优先级。
- 判断产品体验是否成立。
- 提供试用反馈。
- 对阶段性结果做最终验收。

Product Owner 不需要承担前后端架构师职责。

### Main Thread / 技术产品管家

由长期主线程承担，负责：

- 维护产品纲领、架构原则和路线图。
- 拆解任务并写清任务卡。
- 选择哪些任务交给执行 Agent。
- 审查实现结果和测试证据。
- 管理风险登记册、ADR、回滚策略。
- 防止架构漂移、重复造轮子、无边界重构。

### Execution Agent

执行 Agent 只处理边界明确的任务，负责：

- 按任务卡实现具体代码或文档。
- 先列测试用例，再实现。
- 运行指定检查命令。
- 汇报修改文件、测试结果、残余风险和回滚方式。

执行 Agent 不应自行扩大范围。

### Review Agent

Review Agent 不写代码，只审查：

- 权限绕过风险。
- 数据泄漏风险。
- 审计缺失。
- 测试缺口。
- 架构违背纲领。
- 重复造轮子。
- 不可维护临时代码。
- 回滚困难。

## 3. 标准开发流程

每个功能必须走以下流程：

1. 需求澄清：说明目标用户、业务目标、输入输出和约束。
2. 规格设计：写清功能范围、权限、数据、失败场景和完成标准。
3. 测试设计：列出正常路径、异常路径、权限路径和回归风险。
4. 测试优先：能自动化的测试先写；不能自动化的写手动验收步骤。
5. 实现：执行 Agent 只按任务卡实现，不扩大范围。
6. 自检：执行 lint、typecheck、build 和相关测试。
7. 独立审查：由主线程或 Review Agent 审查 diff、测试和风险。
8. 产品验收：必要时由用户体验关键路径。
9. 提交与记录：提交信息、测试证据、残余风险和回滚方式必须清楚。

## 4. 测试优先原则

本项目采用 Spec-first + Test-first + Review-gated，而不是无约束地先写功能。

硬规则：

- 没有验收标准，不进入实现。
- 没有测试用例列表，不进入实现。
- 高风险路径必须自动化测试。
- 无法自动化的测试必须有手动验收步骤。
- 不允许删除或削弱已有测试来让构建通过。
- Bug 修复必须尽量增加回归测试。
- Agent 失败案例应优先沉淀为 eval。

优先测试层级：

1. Schema / Contract 测试：Agent manifest、API response、输入输出 schema。
2. 权限测试：用户、知识库、Agent、导出权限。
3. Model Gateway 测试：mock provider、错误处理、用量记录、超时。
4. Workflow 测试：任务状态流转、人工确认、重试、失败恢复。
5. RAG 测试：固定小文档集、引用来源、权限过滤、空知识库。
6. UI 关键路径测试：登录、上传、生成、确认、导出。
7. Agent eval：结构、引用、缺失项、敏感信息和无依据承诺。

测试目标是风险驱动，而不是覆盖率崇拜。

## 5. 每个任务的最低交付要求

执行 Agent 完成任务时必须汇报：

- 修改文件列表。
- 新增或更新的测试。
- 实际运行的命令和结果。
- 未覆盖的测试风险。
- 是否修改数据库 schema 或迁移。
- 是否影响权限、审计或导出。
- 回滚方式。

没有这些证据，不能视为完成。

## 6. Git 风险控制

推荐流程：

- `main` 必须保持可运行。
- 每个功能使用独立分支，默认前缀 `codex/`。
- 大功能拆成多个小 PR，避免巨型 PR。
- 不混合无关格式化、重构和业务功能。
- 合并前必须通过 lint、typecheck、build 和相关测试。
- 权限、数据库、知识库、导出相关改动必须额外审查。
- 阶段性稳定点应打 tag 或记录可回滚提交。

禁止：

- 未经确认使用 `git reset --hard` 清理工作区。
- 在同一个提交里混入无关改动。
- 为了通过检查删除测试、绕过权限或关闭审计。
- 在不理解现有 diff 的情况下覆盖他人改动。

## 7. 回滚机制

每个功能设计时必须考虑回滚：

- 是否可通过配置禁用？
- 是否影响已有数据？
- 是否有数据库 migration？
- migration 是否可重建或有备份策略？
- 旧入口是否保留？
- 出问题时如何切回旧路径？

高风险功能优先使用 feature flag 或可禁用配置：

- Agent 可禁用。
- Provider 可切回旧配置。
- 新知识库管线可保留旧路径。
- 新 UI 可保留旧入口直到验证完成。

## 8. 复用优先检查

每个较大功能开始前必须回答：

- 社区是否有成熟项目可复用？
- 我们是直接使用、包装、借鉴，还是自研？
- 为什么自研是必要的？
- license 是否适合未来商业化？

默认优先复用成熟生态。

## 9. 文档与决策记录

重要决策必须进入文档：

- 产品原则写入 `docs/LOCAL_AGENT_PLATFORM_PRINCIPLES.md`。
- 开发机制写入本文件。
- 风险写入 `docs/RISK_REGISTER.md`。
- 重大架构选择写入 ADR 或 `ARCHITECTURE.md`。
- 任务拆解写入 `docs/tasks.md` 或规格目录。

AI Agent 不应依赖口头上下文长期记忆。
